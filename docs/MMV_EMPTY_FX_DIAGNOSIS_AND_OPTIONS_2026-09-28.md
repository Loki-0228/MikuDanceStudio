## 数据准备问题

### F01：空 FX 的完整输入准备

`mmv_host::Evaluate` 在插件已加载时逐帧构建 `ModelSnapshot`，随后 `Evaluation` 构造函数复制网格并调用 `Snapshot::FromFrame`。空实例分支位于这些操作之后。宿主快照与插件求值合计约占本次总耗时的 94.7%。

候选方案是在 `MmvPluginApi` 增加可选的本帧需求查询。宿主先提交轻量帧信息与对象目录，插件确定本帧生效的 FX 及依赖，宿主再构造输入。没有数据消费者时，插件只维护工程、启用状态、对象身份及失效信息。

适用条件是没有 FX、烘焙回放、捕获、历史查询或编辑器检查器需要完整 source。需要完整快照的消费者必须参与需求合并。不能仅在 `Evaluation` 后半段提前返回，也不能保留上一帧的活动代理或图像，使关闭 FX 后残留输出。

拟改位置：MMS `src/mmv_host/host.cpp`，MMV `include/mmv/mmv.h`、`src/mmv/plugin.cpp`、`runtime.cpp`、`runtime.hpp`。

验收包括空 FX、FX 关闭后重绘、同帧重新启用、对象增删及烘焙回放。记录实际快照次数、复制字节、更新接受状态和阶段时间。轻量路径的成功必须可区分于更新失败或未执行绘制。

### F02：重复数组与静态数据构建

宿主建立当前网格、原始顶点和权重。`Evaluation` 再复制网格，`Snapshot::FromFrame` 又建立当前网格、原始表和绑定表。物理形变顶点经过宿主缓存、临时数组和结果数组。模型名称、材质、骨骼信息及关节关联也随快照构建。

可能方案包括以下几项，实际范围取决于需求协商后的剩余热点：

- 按对象 generation 和结构版本保存不可变拓扑、原始顶点、权重、名称及绑定定义。每帧只更新消费者需要的动态通道。
- 让只读快照共享不可变数组，仅在形变器写入对应通道时生成独立副本。旧历史快照继续持有旧数据。
- 将只供当前同步调用读取的表表示为受控只读视图。跨调用保存、异步 GPU 提交或历史查询必须拥有数据或延长其生命周期。
- 复用动态数组容量，避免逐帧销毁和重新分配。原始表、形变表的语义必须分别保留，不能因数值暂时相同而合并成可共同写入的数组。
- 对宿主按关节逐个搜索约束的路径，候选方案是每个对象建立一次约束索引，并在约束变化时失效。附件网格若仍有重复克隆，则按需求及几何版本缓存。Rou 本次没有附件，不能据此承诺附件收益。

拟改位置为 `ModelSnapshot`、`AccessorySnapshot`、`physics_input.inl`、`Evaluation`、`deformer_snapshot.cpp`。风险集中在模型删除后地址复用、表情还原、材料范围变化和历史快照被后续写入污染。

验收按通道记录分配与复制量，并覆盖模型重新加载、UV 表情、骨骼和材料变化、拓扑生成、烘焙及历史查询。已有空层共享、摘要缓存和直接字段比较继续保留。

### F03：完整对象校验

`ValidateObject` 是已解析出的 CPU 热点。Rou 的完整输入表存在时，每个顶点有 107 次浮点有限性检查，共约 2,083 万次，另有索引、骨骼和物理关联检查。这是源码推导的检查数量，不是硬件指令计数。

候选方案先随 F01、F06 省去未请求的表及对应校验。对于实际传入的数据，静态表在创建或版本变化时校验，动态属性在更新时校验。未变化的不可变数组可以继承校验结果，跨表引用仍需依赖相应骨骼、拓扑或结构版本。

同一输入在多个内部只读副本间传递时，可以传递校验状态。插件输出、外部输入、生成拓扑和依赖表变化仍需经过适用的校验。校验缓存不得仅以裸指针、数组长度或不可靠的声明版本作为依据。

若需求缩减后有限性检查仍是热点，再评估批量检查或向量化实现。NaN、Inf、负零及现有错误定位的行为需要保持。不能通过 fast-math 或关闭输出合法性检查获取性能。

拟改位置为 `deformer_snapshot.cpp` 及快照版本管理。验收包含合法输入的逐帧耗时，以及非有限数、越界索引、失效权重、跨表变化和历史查询的拒绝行为。

### F04：顶点缓冲读取与数组初始化

`ReadVertices` 的纯 CPU 包含样本中，约 65.34% 位于数组 resize 子调用。当前数据不能将该函数全部耗时归因于 D3D9 缓冲锁等待。

无顶点消费者时，可跳过 VB 锁与复制。有消费者时，可复用目标数组，将不依赖锁定数据的容量准备移到锁之前，并明确初始化本次未覆盖的字段。若宿主已有语义一致的 CPU 顶点结果，可评估直接提供该结果，避免再从 D3D9 缓冲读取。

使用 CPU 结果的前提是其已包含本帧正确的蒙皮、表情、附加 UV、边缘标记和坐标变换。GPU 蒙皮路径不得悄悄退回旧帧或未形变顶点。异步读回若会增加一帧延迟，则不能直接替代当前帧输入。

实施前需分别测量容量准备、Lock、复制和 Unlock。验收涵盖 CPU 与 GPU 蒙皮、附加 UV 数变化、模型尺寸变化和设备重置。

### F05：物理输入与轻量状态耦合

`physicsInput` 同时提供时间与播放标记、重力、形变顶点、刚体绑定和关节局部坐标。宿主每次求值清空其缓存，`Snapshot::FromFrame` 会调用它。原生图层执行还会为时钟信息查询同一回调。

职责边界：Bullet3 求解在 MMS 宿主侧修改。MMV 不改 Bullet3 求解器，只按效果需求读取 MMS 提供的物理输入；MMV 快路径仅在没有物理消费者时跳过自己的输入准备。

候选方案是将时间、播放状态、逐帧状态和重力分为可独立请求的轻量信息，将物理顶点、刚体绑定、关节信息分别按需提供。物理时钟可以独立于某个模型存在，使无模型的图像 FX 也能取得正确时间。

刚体和关节定义可按结构版本缓存，当前姿态及形变几何按本帧需求更新。只有需要原生物理接管的求解器才使用对应接管流程，几何或图像 FX 不应触发接管。未知旧插件保留完整输入。

风险是将“未请求”误当成“物理关闭”或“真实空表”。验收要求仅颜色、仅顶点 FX 不构建物理数组，物理 FX 仍得到完整数据，接管与恢复保持正确，录制时间步不受渲染速度影响。

### F06：输入需求需要细于 FX 类型

MME 兼容 FX 可能读取骨骼或表情控制值，MMV 新标准 FX 可能只读取位置。纯颜色辉光可以完全不读取模型顶点。现有 `readChannels`、`writeChannels` 可作为通道级起点，但 `MESH` 仍不足以表示这些差别。

候选方案是按本帧有效输出反向遍历 pass 依赖，将读取、写入、校验及合成需求合并。需求还需说明对象或材质范围、source/upstream/history 来源及执行阶段。

| 数据组 | 可独立表达的需求 |
| --- | --- |
| 帧信息 | 时间、相机、光照、输出尺寸、导出状态 |
| 图像 | 场景颜色、深度、法线、遮罩、阴影、上游或历史结果 |
| 顶点 | 位置、法线、UV、各组附加 UV、边缘属性 |
| 结构与材质 | 拓扑、材质分组、材质参数、纹理引用、纹理像素 |
| 骨骼与表情 | 名称和稳定键、当前姿态、绑定姿态、表情值 |
| 蒙皮绑定 | 原始顶点、权重、顶点映射 |
| 物理 | 刚体、关节、形状、绑定、重力和时钟 |

原生模块可以声明能力，兼容 FX 根据实际语义、脚本绘制和依赖解析补充。反射或静态解析无法证明动态访问范围时，应保守取得完整输入，不能仅凭文件名含 Bloom 或文件扩展名分类。

只写顶点位置的 FX 仍需保留其他原有属性。候选方式是按字段合并输出或让渲染资源继续持有未变化部分；生成拓扑的效果必须提供新的映射和必需关联。

验收以请求字段和实际读取量为准，覆盖纯颜色、仅位置、材质 FX、ControlObject、物理 FX、混合依赖和未知旧 FX。启用曲线及热重载必须在当前帧更新需求。

### F07：重复发现、重绘和缓存失效

宿主为每次求值递增 `frameId`，因此时间轴停在同一点时，运行时按 `lastFrame_` 的重用条件仍不会命中。`Runtime::Evaluate` 还会执行 `Discover` 和效果文件时间检查。此路径存在，独立收益尚未量化。

候选方案是区分求值序号与输入版本。对象目录、名称和材料结构按变化更新，文件热重载按文件通知或有界检查节奏失效。动态输入缓存依赖相机、灯光、姿态、材料、效果参数和设备等实际版本。

按需路径仍需推进编辑态物理、更新时变 FX 和生成当前帧图像。不能只比较 `timeSeconds`，也不能重复使用同一求值序号来规避求解器的重复提交检查。

验收覆盖时间轴不变但相机移动、参数修改、编辑态模拟、FX 开关、文件热重载和导出重绘。先测量发现和文件查询成本，再决定是否纳入相应批次。

## 图像与导出问题

### F08：纯图像 FX 的执行时机

当前 `mmv_host::Evaluate` 位于模型绘制前，不能直接读取本帧最终场景颜色。减少顶点输入不会自动产生该图像。

候选方案是在帧开始计算需求，在正常模型绘制和必要的场景合成完成后执行图像 pass，并在呈现与录制读回前完成最终合成。深度、法线或指定物体颜色按明确请求产生或引用。

图像 pass 应区分本帧、上游和历史资源，避免边读边写同一渲染目标。需要重新绘制模型的兼容脚本仍保留几何需求。不同 pass 的顺序必须遵守效果依赖，不能统一延后所有效果。

拟改位置包含 `frame_scene.cpp`、宿主图像服务及 MMV pass 调度。验收检查纯图像辉光不读取模型顶点，正常场景仍完整绘制，画面没有一帧延迟，录制成品与最终合成一致。

### F09：图像输出依赖几何代理

宿主处理 `MmvOutputImageExtension` 时，只有对应对象的 proxy 存在、活动且 generation 匹配，才上传图像。真正不生成网格代理的全屏 FX 需要独立的输出约定。

候选方案是让图像输出声明帧、图层或对象作用范围，并持有独立输出身份、源 generation、有效帧与资源版本。对象图像仍校验对象是否存在，全屏图像不要求创建虚假网格代理。

旧图像扩展保留原语义，新扩展通过能力位及结构大小协商。释放责任、跨调用持有、设备重置和取消导出时的资源销毁必须写入契约。

验收包含无几何代理的全屏 FX、对象删除、模型重新加载、关闭 FX 后清屏、旧插件组合和失效图像拒绝。

### F10：图像读回、转换与重新上传

兼容模块 `ReadBackSurface` 使用 `GetRenderTargetData` 并生成 CPU RGBA32F 像素。宿主 `UploadLegacyImage` 每次新建 D3D9 托管纹理，将像素转成 A8R8G8B8，再上传合成。视频编码还有最终画面读回。这些分支不属于本次空 FX 的实测原因。

可能方案按设备条件选择：

- 在可共用设备与兼容资源时，传递受控 GPU 图像引用，在宿主直接合成。
- 跨设备或跨 D3D9、D3D12 时，先验证适配器、格式、共享句柄和同步能力。满足条件才使用共享资源。
- 无法共享时，复用暂存表面、CPU 缓冲和宿主纹理，减少逐帧创建。转换路径保留现有格式、Alpha 和精度行为。
- 需要流水处理时，以输出帧序号管理缓冲和完成事件。最终合成必须等待本帧结果，不能以读取上一帧替代等待。

资源传递需要 F08、F09 的执行阶段与生命周期契约。验收分别统计读回、转换、分配、上传和合成时间，并覆盖 DX9、DX12、不同适配器、软件回退、HDR 数据、透明合成及设备丢失。

### F11：线程额外 CPU 消耗

同一固定程序的 4 线程与 1 线程对照分别为 107.62 和 110.57 ms/帧，两组都有超过 5% 的波动。整个子进程累计 CPU 时间中位数分别为 55.26 和 18.30 秒，包含启动与预热。减线程降低了 CPU 消耗，未解决帧耗时回退。

候选方案是先完成数据准备优化，再隔离蒙皮、排序工作线程的计算、自旋和阻塞等待。若确认存在空转，可评估受支持的等待策略、有界工作线程或持久任务调度。具体选择需以当前 OpenMP 运行时实际支持和测量为准。

不将全局固定单线程列为当前首批修复。它可能损害多模型蒙皮和排序性能。验收同时记录帧时间、CPU 时间、线程等待和多模型结果，不能只依据任务管理器占用下降判定性能问题解决。

### F12：AVI/H.264 兼容与导出状态

源码检查确认 MMV 求值和 `DrawLegacyImages` 位于录制读回之前。AVI 使用 DirectShow 推帧，H.264 使用 `StartBuiltInH264Recording`、`WriteBuiltInH264Frame` 和 `FinishBuiltInH264Recording`，两者消费同一份录制像素。尚未完成实际导出文件验收。

2026-09-29 核对 MMS 与 MMV 源码后，确认 H.264 编码器属于 MMS；编码器从共享 D3D9 capture readback 接收像素，MMV 没有直接调用编码器的 ABI 回调。MMS 每帧已向 `MmvFrame` 传入 `timeSeconds`、`elapsedSeconds` 和当前 D3D viewport 的宽高。当前 `MmvFrame` 没有导出会话、帧序号或录制状态字段。

下一步先做导出实测，核对现有时钟和尺寸字段是否足够让 MMV FX 生成对应输出帧，并确认录制目标确实包含 MMV 图像及代理。不要先增加 H.264 专用接口。只有实测发现现有 `MmvFrame` 无法表达必要的导出语义时，再设计可选 ABI 字段；MMS 继续拥有 H.264 编码职责。

已与负责 MMS 改动的会话核对：当前字段是预期的基础合同。若 FX 不需要识别导出状态或最终导出尺寸，无需新增录制字段；若有这类 FX 需求，应先定义具体行为，再决定是否扩展接口。

图像后处理在录制读回前完成。导出分辨率变化时，按实际渲染目标和视口重建图像资源，并使受尺寸影响的缓存失效。不能把编辑器窗口尺寸当作导出分辨率。

物理推进使用时间轴差值，编码器背压只影响导出速度。导出开始、结束、取消、seek 和重复导出需要明确的状态重置或恢复规则。同一输出帧重绘不得重复推进模拟，历史图像与物理状态不得串入下一次导出。

拟改位置为 F05 的帧上下文、宿主录制边界、MMV 时钟和图像生命周期。MMS 保持 AVI/H.264 编码职责。新接口的签名与头文件声明在实施前统一核对，避免各调用点独立声明后发生参数不一致。

验收矩阵包括 AVI、H.264，两种输出帧率 30 和 60 FPS，非零起始帧，输出尺寸变化，连续导出、取消后重试及含物理、历史帧和纯图像 FX 的场景。检查实际帧数、时间戳、时长、方向、颜色、Alpha 处理和音画时间关系。H.264 有损画面比较采用预先说明的容差，同时保留编码前像素作为参照。

## 测量、正确性与构建问题

### F13：阶段计时覆盖不足

`uploadMilliseconds` 只累计代理网格 `Upload`，没有包围 `UploadLegacyImage`。现有主基准没有独立输出 GPU compute、readback 或 D3D9 绘制时长。未采到的指标不能记为零。

候选方案是将需求计算、宿主快照、插件准备、GPU 提交与执行、读回、图像转换、网格上传、图像上传、合成、最终录制读回和编码等待分别记录。嵌套计时要标明包含关系。增加实际请求字段、复制字节、回调次数与资源创建计数，以确认省略了哪些工作。

CPU 计时与 GPU 时间戳分别标记。GPU 查询优先延后读取已完成结果，避免每帧主动 Flush 或等待查询改变待测负载。现有带等待的 profiling 只作诊断，不与关闭计时的正式性能结果混合。

这类源码计时改动也须审批。验收包括计时开关自身开销、缺失数据标记、阶段覆盖及图像上传实际被计入。

### F14：GPU 跟踪覆盖与系统符号

已有 ETL 未报告事件丢失，但 WPA GPU 表中 B 进程记录在约 17.5 秒截止，而进程持续到约 41.8 秒。日志还出现 `Duplicate start TraceLogging activity`。该导出表已经排除，不能用于量化 GPU 时长或判断 GPU 饱和。部分系统函数符号仍未解析。

候选处理是用更短的单进程记录核对进程起止、采样区间和 GPU 包覆盖，确认 GPU 工具确实支持当前 D3D9 路径。符号按实际加载模块匹配 PDB，并保留版本信息。若 ETW 导出仍不完整，可用经验证的 D3D9 GPU 时间戳查询补测，记录设备不支持和 disjoint 情况。

Windows GPU Engine 计数器可作为活动证据，不能替代每帧 GPU 时间，也不能把不同引擎百分比相加。验收要求导出覆盖完整测量区间、进程匹配、事件丢失情况可说明，且 CPU 与 GPU 指标有明确边界。

### F15：基线波动与场景可比性

主 ABBA 中 MME-only 的相对极差约 17.52%，但绝对极差为 0.61 ms。线程对照两组波动也超过 5%。另有初次 ABBA 被 ETW 收尾干扰，以及 GPU 补采时存在其他 MMS 进程的记录，均已单列。

候选处理是冻结两套源码与运行副本，在相同模型、动作、相机、分辨率、设备、物理、FX 和透明排序配置下交替采样。排除原因事先写明，失败与异常原始结果仍保留。微小收益需重复采样支持，不能与约 105 ms 的当前回退采用相同精度解释。

当前隐藏强制编辑器基准只能度量其对应负载。播放 FPS 需要另行验证实际播放与 Present 时序。后台采集若无法保持同等绘制工作量，应标为尚无有效播放结果，不能直接换算已有吞吐率。

正式前后比较记录提交、未提交差异、构建参数、EXE/DLL 哈希、采样环境、P50/P95 和全部批次结果。其他会话的构建输出不覆盖固定副本。

### F16：图像差异与动态正确性缺口

MME-only 与空 MMV 的静态 PNG 有 44 个不同像素，最大单通道差为 21。差异原因尚未定位。线程数对照的首对静态 PNG 完全相同，但该结果不覆盖动态物理或实际 FX。

候选处理先在同一版本重复捕获，判断差异是否来自确定性不足，再定位差异区域及对应渲染阶段。候选因素包括覆盖绘制顺序、数值舍入和状态恢复，当前不将任何一种写成已证实原因。比较时同时保留完整成品和必要的阶段图，不能通过隐藏发生差异的绘制内容获得一致。

动态验收分别覆盖物理播放、透明排序各档、MME 兼容 FX、纯图像 FX、FX 开关与热重载、模型增删、烘焙和历史查询。确定性场景要求相同结果；允许数值或编码差异的场景先明确容差，再检查误差分布及可见结果。

### F17：诊断构建的清单错误

诊断构建时曾发现宿主清单缺少 `</security>`，EXE 因 SideBySide 59 无效 XML 无法启动。此前只向隔离诊断 EXE 嵌入已提交的有效清单，并保留原文件。该记录不表示当前工作区仍有同一错误。

候选处理是先核对当前 `res/mmd_manifest_x64.xml`。如果问题仍存在，修复 XML 结构并保留原权限与兼容设置，再以常规构建生成有效 EXE。不能用调整权限等级或清除安全配置替代 XML 修复。

前后性能版本必须使用一致的有效清单处理方式。验收涵盖清单解析、EXE 启动和相关系统错误记录。重新构建后记录新的二进制哈希。

### F18：共享工作区与 ABI 兼容

两仓库已有其他会话修改，MME 兼容模块也在继续演进。旧插件可能依赖完整输入。若未经协商直接传空数组，插件无法分辨未请求与真实空数据。

候选方案在实施前明确文件归属，记录两仓库工作区状态与差异，并冻结被测版本。改动仅覆盖批准范围，不恢复或覆盖其他会话的文件。跨模块合入后重新构建并测量，不能套用旧副本的基线。

接口扩展使用可选尾部、`structureSize` 和能力标记，保持旧前缀与数组元素步长。需求、有效位和资源生命周期分别表达。新宿主遇到旧 DLL 走完整路径，新 DLL 接收旧宿主完整输入时仍能工作。原生模块已有通道声明，也要核对缺失字段契约后才能裁剪。

验收覆盖新旧宿主与插件组合、缺失必需输入、设备重置、模型 generation 变化和兼容模块回归。其他会话的完成状态不能替代本任务的整合验收。

## 2026-09-29 需求查询缓存与按需快照设计

### 当前快照范围

当前 `MmvInputDemand` 只有 `NONE` 和 `SCENE` 两种结果。MMS 每次求值都会先构造对象身份、模型名称、材质名称、骨骼名称和变形名称，再调用 `queryInputDemand`。只要回调返回 `SCENE`，宿主就会清空元数据快照并重建完整快照。

完整模型快照会复制顶点、索引拓扑、原始顶点、蒙皮权重、材质参数、骨骼变换、变形值、刚体状态和关节数据。当前判定只要 `document_.bindings` 非空就返回 `SCENE`，不检查 FX 实际读取哪些字段。因此，一个只读像素资源的 FX 也会触发整份快照。当前确实是全量快照，不是按需快照。

### 缓存查询结果

需求查询的结果不需要每帧重复计算。查询应在插件首次加载、FX 配置或文件变化、对象增删、项目切换和需求相关状态改变后运行。宿主在帧间缓存查询结果。缓存为 `NONE` 时，后续帧不构造对象元数据或完整快照；缓存包含其他需求时，宿主按缓存的需求准备输入。

当前 ABI 2 查询尚未包含需求掩码，且运行时对任何绑定保守返回 `SCENE`。缓存因此只能消除每帧回调和元数据快照的开销，不能减少有绑定场景的数据复制。FX 文件自动重载默认开启，可在 MMV 主菜单关闭。宿主把选项保存在程序目录的 `MMV.ini`；MMV 文件时间变化后重新加载，配置重载会使需求缓存失效。

FX 原生开关可以带关键帧。安全的首版需求掩码应合并某个绑定在所有开关状态下需要的数据，不按当前帧裁剪。这样开关关键帧不会让需求缓存过期，用户切换 FX 仍能得到正确输入。若以后按当前启用状态进一步裁剪，宿主必须在每个开关关键帧边界使缓存失效；漏掉边界会让刚启用的 FX 收到空字段。执行该优化前要比较边界检测成本与每帧查询成本。

### 按数据类别提供快照

ABI 应把帧级资源、对象元数据和对象数组字段分别编码成需求位。查询回调返回各绑定需求的并集。宿主只复制被请求的字段。未请求的数组使用空指针和零计数；该规则必须写入 ABI 契约。旧插件或未知需求继续获得完整快照。

| 需求类别 | 宿主字段或资源 | 可省略的数据 |
| --- | --- | --- |
| 身份与名称 | 对象路径、名称、generation、材质/骨骼/变形名称 | 顶点、索引、变换和物理状态 |
| 材质 | 材质参数、材质纹理路径和纹理资源 | 顶点缓冲、蒙皮权重、物理状态 |
| 网格拓扑 | 顶点和三角形 | 原始顶点、权重和物理输入，除非其他需求需要 |
| 蒙皮 | 原始顶点、蒙皮权重和骨骼变换 | 刚体、关节及物理顶点 |
| 变形 | 变形当前值及 FX 所需的源顶点 | 刚体与关节状态 |
| 物理 | 刚体、关节、重力及物理顶点 | 不参与该物理计算的材质与图像资源 |
| 图像 | 颜色、深度、法线或历史图像资源 | CPU 顶点快照，但前提是 FX 绘制直接复用 MMS 的网格 |

图像类别不能只通过省略 `MmvObject::mesh` 实现。现有 `MMV_HOST_MME_BRIDGE` 以 MMV 输出网格创建代理，图像输出也依赖活动代理。纯像素 FX 需要先有独立的图像执行时机和输出生命周期，并能复用 MMS 网格绘制或全屏绘制。F08 和 F09 已列出对应宿主改动与验收；在这些路径完成前，兼容类渲染 FX 仍需几何输入。

MME 兼容模块尚未完成。完成后应利用 FX 反射识别已知语义和实际 pass 资源，并返回需求位。未知语义、脚本回调或无法静态判断的资源依赖必须采用完整需求。新标准 FX 可在效果声明或编译反射中提供更明确的需求。Bullet3 是 MMS 提供的数据服务；MMV 只在 FX 确实读取刚体、关节或物理顶点时请求它。

## 2026-09-29 未应用 FX 关闭后的需求缓存回退

### 现象与原因

在 MMV 编辑器中拖入 FX 会立即更新编辑预览中的绑定。编辑器打开期间，`QueryInputDemand` 必须保守返回 `ALL`，防止预览中的 FX 在宿主仍使用较窄快照时读到缺失字段。若关闭前已求值预览，MMV 先前还会保留该预览的 `outputs_`、`meshes_`、图像缓存、物理请求标记或附件错误。下一次需求查询发生在新一帧 `Evaluate` 之前，会把这些过期的派生状态当成活动消费者，即使绑定已回滚，也继续请求网格或物理快照。

关闭窗口会回滚到最近一次 Apply 的检查点；若期间没有任何文档变化，也会清除检查点。回滚时丢弃预览求值产生的派生输出、图像和错误缓存，复位原生物理需求状态，然后请求宿主重绘使需求缓存失效。宿主在下一次求值前仅构建身份和名称元数据，再查询已提交配置，并按新的字段掩码生成快照。Runtime 析构时调用的 `CloseEditor` 也经过同一取消路径。

### 修复与验证

- `EditorTransactionAccess::Cancel` 在未变化分支也调用 `Redraw`。此前该分支只释放检查点，可能留下编辑器打开时缓存的保守 `ALL`。
- `UnappliedEffectDoesNotPersistSnapshotDemand` 覆盖模型上拖入 FX、实际求值一次预览以生成派生输出、未 Apply、关闭窗口、检查宿主重绘通知及再次查询需求。关闭前查询为 `ALL`，关闭后绑定和预览输出均清理，需求恢复到编辑前的结果。
- 当前 Release 构建中，该回归用例及“编辑器 Apply 后回滚”用例通过。完整 `mmv_editor_tests` 有 13 个 UI 展开/选择类用例失败；这些失败与快照需求用例无直接重合，且没有相同源码状态的修改前结果，原因未定，不能据此归因本修复。
- 宿主 `Redraw` 回调会置 `inputDemandInvalidated`；主线程下一次求值消费该标志并重查需求。该宿主文件已通过本轮目标构建。

### 后续防护

保留编辑器打开时的保守全量需求，避免预览过程访问缺失数据。若未来将编辑器预览改为延迟提交或事务外维护预览绑定，需求查询仍应只基于活动预览消费者；窗口关闭、取消、应用和 FX 文件重载都必须使宿主缓存失效。验收时继续覆盖 WM_CLOSE、宿主调用 `CloseEditor`、Apply 后关闭和连续打开/关闭场景。
