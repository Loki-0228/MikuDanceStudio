# 莫宁模型的进程 CPU 空转修复

已修复 OpenMP 工作线程在两帧之间持续忙等待的问题。本机「莫宁-微调自用」前后对照中，MMS 进程 CPU 从约 23%–25% 降到约 3%–4%。计算线程上限、蒙皮、透明排序、物理、描边和阴影代码保持原有行为。

修复提交为 `6ca7c98`，已更新本地 `build/Release/MikuMikuDance.exe`；本次没有推送或发布 GitHub Release。此前以 MikuMikudance 932 fix 为参考的定位见[诊断记录](CPU_USAGE_MONING_20261011.md)。

## 修复方式

VCOMP140 在 DLL 加载时读取 `OMP_WAIT_POLICY`。只在程序运行后设置环境变量来不及生效，初版实测仍占用约 23.27% CPU。

最终实现将 VCOMP140 改为延迟加载，在窗口、渲染器及插件初始化前设置进程内的 `PASSIVE` 默认值；几何任务入口也执行一次性初始化，覆盖无窗口调用路径。已有的 `OMP_WAIT_POLICY` 设置继续优先，`OMP_NUM_THREADS` 和最多 8 个几何工作线程的策略保持原样。不写入用户或系统环境变量。

延迟加载要求由几何线程库传递给生产程序和独立验收工具。PE 检查确认修复后 VCOMP140 位于延迟导入表，普通导入表中没有该运行库。

- 两侧测试配置均固定 CPU 蒙皮，避免自动选择不同计算设备。只修改测试副本的配置，不修改正式目录的处理器设置。

## 进程 CPU 结果

表中为两次运行均值，括号为两次运行之间的范围，单位为进程 CPU 百分比。

| 场景 | 修复前 | 修复后 |
| --- | ---: | ---: |
| 原生，静置 | 23.67（23.43–23.91） | 3.06（3.01–3.11） |
| 原生，播放 | 23.74（23.33–24.16） | 3.55（2.76–4.35） |
| MMV4MMS，静置 | 25.10（25.06–25.14） | 3.72（3.64–3.79） |
| MMV4MMS，播放 | 24.35（23.92–24.78） | 3.48（3.44–3.53） |

各组均值下降约 85%–87%。同一 VCOMP140 文件的只读状态检查显示，修复前忙等待标志为 1，修复后为 0。原生静置首轮中，修复前七个工作线程各消耗约 11.89–12.02 CPU 秒，修复后约 0.42–0.52 CPU 秒，采样时间均为约 12 秒；线程团队没有缩减。

上述数字是实际运行窗口的进程占用，不能解读为等 FPS 的渲染加速。内部帧计数有短时波动：原生修复后两轮静置中位数为 51、57.5，播放为 54.5、57；修复前为 57–58。部分原生修复后秒样本曾降至 15、18、23，原始记录保留，这些异常区间不用于证明等帧率性能收益。MMV4MMS 组也未稳定达到上限。没有将这些计数或下述吞吐率换算成已测得的实际显示 FPS；本次没有测量 GPU 时间或成功 Present 的显示率。

## 正确性和吞吐检查

四项回归测试全部通过：运行库必须延迟加载、默认等待策略、显式 ACTIVE/PASSIVE 设置、指定 3 个线程及最多 8 个线程、反复并行计算的完整结果。测试日志位于 `geometry-workers-tests.log`。

两侧生产核心各自构建 `frame_benchmark`。使用相同相机和 800 × 450 视口，预热 30 帧、采样 60 帧，从渲染目标直接保存画面，不使用桌面截图。四次完整渲染中，每次 90 帧视口检查均通过，模型和物理对象数量一致，CPU 蒙皮更新数一致，未发现模型、描边或阴影缺失。

等待 GPU 完成后的每帧批次耗时：修复前两轮为 9.447、8.998 ms，修复后为 9.529、8.882 ms。两轮均值分别约 9.223、9.205 ms；该项属于强制编辑帧吞吐检查，不是播放 FPS，也不是纯 GPU 时间。

严格逐像素相同的初始门禁没有通过，未将其记为通过：两轮前后画面对比分别有 175、325 个不同像素，占 360,000 像素的 0.049%、0.090%；最大通道差分别为 5、28。旧版本自身两次回读也有 230 个不同像素，新版本自身为 260 个，说明重复运行存在波动。画面结构检查通过，但本次不声称像素级完全一致。

另用两侧工具回读完整蒙皮顶点缓冲区，7,479,168 字节逐字节一致，SHA-256 均为 `87fd7397d58f1a7e2c09425581bc7dcefaa3ec23d977bbd00bf4decbb169cf73`。该检查仅验证几何正确性，没有用其简化的工作负载计算 CPU 收益。MMV4MMS 的检查限于生产进程 CPU 和状态；本次未做该插件的像素级对照。
