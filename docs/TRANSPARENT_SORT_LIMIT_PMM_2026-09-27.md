本文保留六档测试版本的历史行为与证据；当前五档、默认值及存档规则见[五档排序记录](TRANSPARENT_SORT_FIVE_TIERS_2026-09-27.md)。

本功能已于 2026-09-27 从 `fix/cloud-precision` 合入本地 `main`，正式入口为 `build/Release/MikuMikuDance.exe`。合并验证与版本位置见[主分支集成记录](CLOUD_SORT_MAIN_INTEGRATION_2026-09-27.md)。以下保留候选开发阶段的双 build 证据。基线生产源码为 `a9ff731`，基线分支 `baseline/cloud-auto`；首轮测试源码固定在 `fd7cc66`（前）和 `37c5b01`（后），其后仅修订深层压力驱动，最终为 `34a39e3`（前）和 `508aed5`（后）。每轮前后使用相同驱动源码，清单记录 SHA-256；后续测试调整没有修改生产渲染、菜单或存档代码。

## 用户行为

「显示 → 透明排序上限」提供关闭、低（快速）、标准（默认）、高、极高、最高六个互斥选项。移除原独立开关；程序内部也只有一个枚举值。关闭覆盖原档位，不保留上次选择。旧命令 303 仅作为宏兼容入口，在关闭和标准之间切换，不恢复历史值。

PMM v2 只保存所选上限，包含最高和关闭。正常保存、重开与另存使用同一字段，不保存当前层数或相机统计。旧双字段工程读取后转换为单档位，再保存时退休合法的旧开关记录。未知格式的原始记录在用户未编辑时保留，明确选择一个档位后再规范化。字节值和边界见 [PMM v2 扩展格式](PMM_V2_EXTENSIONS.md)。

这是 MMS 相对原版 MMD 新增的排序与工程设置行为；原版 MMD 不会使用此设置。原 Toon、模型参数、Cloud.fx、相机和素材未修改。

## 最高上限的工作量

标准、高、极高保持 1024、2048、4096 次分层迭代上限。最高采用当前参与排序、裁剪后的三角形数量加一：单个三角形在一个像素最多贡献一层，多出的一次用于空查询确认完成。沿用每层已有的遮挡查询，片段耗尽即结束，没有独立计数预扫描。

这个值是安全上界，不是预先算出的最小层数。当前云镜头包含 21,412 个参与排序的三角形，最高上界 21,413，实际 668 层就完成。分层须完整完成后才提交；遇到设备/效果错误则丢弃私有中间结果，并回退完整几何。

最高只在支持的内置 SM3 分层路径上动态推进。自定义 MME shader、SM2、固定管线或资源不足时，BSP 回退使用现有极高预算（额外 400 万三角形、深度 512、epsilon 2e-13），仍可能近似排序。配件 `.x` 的独立通道和 MSAA 部分覆盖的限制沿用 [浮点合成记录](CLOUD_FLOAT_COMPOSITING_2026-09-26.md)，不能据此声称所有效果都已精确排序。

## 构建与后台验证

两个 build 均为 VS 2022 / v143 / x64 Release，`MIKUDANCESTUDIO_DIAG=OFF`、`MIKUDANCESTUDIO_PERF=OFF`，使用同一 Conan toolchain。测试窗口以 `SW_HIDE` 创建，进程 `CREATE_NO_WINDOW`；图片来自被测渲染目标，不使用桌面截图。构建命令、Git 状态、EXE/DLL/配置哈希、原始日志及每次命令均在 `.local/artifacts/cloud-auto-pmm-20260927/`。

### 保存、重开、另存

新版通过六档逐一真实读写、单选标记、三语言菜单、重复选择不标脏、最高转关闭、旧双字段迁移、未知值保留与显式替换、运算器独立、新建/旧文件/CRC 隔离。旧版相同驱动在“新存档不应含旧开关记录”断言失败，保留为预期反例。扩展 codec 两侧均通过 145 项检查。新版另以真实 `ToonCloud.pmx` 重跑全部 PMM 用例并通过，核对模型数据与设置共同往返；几何排序回归也通过。

独立解析实际文件尾部并检查 CRC 后，旧版的排序设置有两个字段（开关 1、精度 0）；新版最后选择关闭后只有 `transparent_sort_precision = [5]`。没有上次精度字段。见 `checks/pmm-byte-inspection.json`。

### 当前云镜头的图像与耗时

使用未修改的云工程副本，MME 加载、Cloud.fx 关闭、ikParticle.fx 保留。原视角、1076×606 视口、8x MSAA；每次预热 2 帧、测量 5 帧，按前/后/后/前顺序运行。两边请求值均为 4，JSON 明确区分：旧版尚不支持此命令，实际仍为标准 1；新版实际为最高 4。

| 轮次 | 修复前，GPU 完成后的批次 ms/帧 | 修复后，GPU 完成后的批次 ms/帧 |
| --- | ---: | ---: |
| 1 | 585.250 | 587.791 |
| 2 | 646.758 | 606.985 |

四张读回图像 RGBA 逐像素完全一致，尺寸 1463×914（含视口外目标区域）。这是 GPU 完成后的批次吞吐耗时，不是桌面播放 FPS；波动大于平均差值，不能声称本次提速。当前镜头最高与标准均实际完成 668 层，追加的最高上限没有增加该镜头的层次数量。

测评驱动第一次带 `--verify-view-toggles` 的诊断因仍检查旧菜单 303 而退出 44。失败文件保留，不纳入计时表；修正前后共用驱动后，该诊断通过，实际最高值和 668 层记录在 `cloud-abba/after-view-check*`。正常计时运行未启用该诊断分支。

### 深层透明专项

测试使用 1152 层与 4608 层的 alpha=1/255 黑色面，白底参考值分别约 2.76 和 0.00，RGB 容差 2，目标 A 必须为 255。同一测试源码在两个生产核心上分别构建，并测试单采样和 4x MSAA。初次驱动继承了原测试的 `D3DCREATE_SOFTWARE_VERTEXPROCESSING`，与生产云测评的硬件顶点处理不同。旧版两种采样模式均得到白色 (255,255,255)，各有 18 个失败样本，trace 在 1024 层回退。新版单采样先触发 180 秒超时，延长后通过：1152 层为 (3,3,3)，4608 层为 (0,0,0)，A 均为 255，实际完成 1152/4608 层；整组用时约 443 秒。软件顶点处理的 4x MSAA 组在 600 秒超时，1152 层通过，4608 层未完成。这些长耗时不能当作生产版性能。

随后把最高模式改为与生产相同的硬件顶点处理，并打印、断言实际设备标志为 `0x40`。96×96 的旧版硬件两组仍各有 18 个错误采样点；新版全尺寸硬件运行由协调者提前停止，保留为未验收诊断，不将未完成结果写成通过。

常规层数边界测试随后改为 16×16 目标，前后两侧同步相同驱动，仍保留全部 1152/4608 层、原 shader、alpha、九个采样点和完整解析式断言。只减少重复填充面积，不减少层数或几何，不用于生产性能比较。`--maximum-full-size` 仍可运行原 96×96 压力用例，支持附加 `--msaa`。真实云图的 1076×606 视口及性能采样从未缩小。硬件全尺寸诊断见 `hardware-checks/`，常规有界测试结果见 `compact-checks/`，软件路径与超时证据仍保留在 `checks/`。

最终 16×16 硬件路径对照结果如下，四组使用相同驱动源码和设备标志：

| 模式 | 修复前 | 修复后 |
| --- | --- | --- |
| 单采样 | 1152/4608 层均输出 255，18 个采样失败 | 分别输出 3 / 0，全部 RGB 与 A255 检查通过 |
| 4x MSAA | 1152/4608 层均输出 255，18 个采样失败 | 分别输出 3 / 0，全部 RGB 与 A255 检查通过 |

新版 trace 分别记录 `layers=1152/4608 complete=1 committed=1`；旧版均在 1024 层未完成并回退。新版两组完整进程约 11.4 / 11.1 秒，旧版约 3.6 / 3.5 秒；这些是专用正确性用例的总耗时，旧版没有完成相同透明工作，不能据此评估生产 FPS 或声称等画质加速。软件路径 96×96 单采样的通过作为额外证据保留，96×96 MSAA 超时仍标记为未验收。

标准档的低 alpha、低 alpha + 4x MSAA、相交面 + 4x MSAA、预算耗尽回退四项在前后两个 build 均通过（8 次独立运行），记录于 `standard-regressions/`。最高档新增的测试尺寸没有改变这些原用例。没有重跑全量 CTest；历史自阴影 alpha 未解决样本仍按原文档保留。
