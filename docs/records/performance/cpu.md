## 莫宁模型的进程 CPU 空转修复

原始记录：`CPU_WAIT_FIX_20261011.md`。其中的版本、日期和验证范围沿用原记录。

已修复 OpenMP 工作线程在两帧之间持续忙等待的问题。本机「莫宁-微调自用」前后对照中，MMS 进程 CPU 从约 23%–25% 降到约 3%–4%。计算线程上限、蒙皮、透明排序、物理、描边和阴影代码保持原有行为。

修复提交为 `6ca7c98`，已更新本地 `build/Release/MikuMikuDance.exe`；本次没有推送或发布 GitHub Release。此前以 MikuMikudance 932 fix 为参考的定位见[诊断记录](cpu.md#record-cpu-usage-moning)。

<a id="record-cpu-wait-fix-修复方式"></a>
### 修复方式

VCOMP140 在 DLL 加载时读取 `OMP_WAIT_POLICY`。只在程序运行后设置环境变量来不及生效，初版实测仍占用约 23.27% CPU。

最终实现将 VCOMP140 改为延迟加载，在窗口、渲染器及插件初始化前设置进程内的 `PASSIVE` 默认值；几何任务入口也执行一次性初始化，覆盖无窗口调用路径。已有的 `OMP_WAIT_POLICY` 设置继续优先，`OMP_NUM_THREADS` 和最多 8 个几何工作线程的策略保持原样。不写入用户或系统环境变量。

延迟加载要求由几何线程库传递给生产程序和独立验收工具。PE 检查确认修复后 VCOMP140 位于延迟导入表，普通导入表中没有该运行库。

## 「莫宁-微调自用」模型的 MMS 进程 CPU 排查

原始记录：`CPU_USAGE_MONING_20261011.md`。其中的版本、日期和验证范围沿用原记录。

2026-10-11 的后台实测确认，MMS 持续高 CPU 的主要来源是 OpenMP 工作线程的主动等待。主线程按帧率上限休眠时，7 个工作线程仍持续消耗 CPU。保留 8 线程、仅为测试进程设置 `OMP_WAIT_POLICY=PASSIVE` 后，进程 CPU 从约 23% 降至约 2%～3%。当前 v2026.10.11.3 携带本机 MMV4MMS 插件的补查也复现了这一差异。

本次只诊断原因。没有修改生产源码、正式 EXE、模型、系统环境变量或用户设置；等待策略只传给测试子进程。该实验不构成已交付的性能修复。

<a id="record-cpu-usage-moning-进程-cpu-的测量口径"></a>
### 进程 CPU 的测量口径

所有百分比都来自被测进程自身累计的用户态和内核态 CPU 时间，没有采集或使用系统总 CPU 占用。

`进程 CPU 占用率 = 100 × 进程 CPU 秒数增量 ÷ 实际经过秒数 ÷ 32`

本机有 32 个逻辑处理器，因此一个逻辑处理器持续繁忙相当于约 3.125%。线程数据也只查询被测 PID。采样器和其他程序的 CPU 不计入被测进程，但机器资源竞争仍可能影响运行波动。

测试副本运行在未显示的独立 Windows 桌面，主窗口隐藏且未最小化，没有切换用户桌面。程序使用正常消息循环；没有修改被测进程内存，没有跳过绘制或 Present。每秒读取帧率限制、程序帧计数、模型数量、播放状态和渲染门状态，以排除启动未完成或停止刷新的样本。

表内帧计数是程序自身的一秒计数，供检查工作量是否持续。它不是 ETW 成功 Present FPS，也不是 GPU 时间。调用栈在 CPU 采样结束后另行采集，避免暂停线程影响表中的 CPU 结果。

<a id="record-cpu-usage-moning-工作线程为什么持续占用-cpu"></a>
### 工作线程为什么持续占用 CPU

`include/mikudancestudio/geometry_workers.hpp` 中的 `GeometryWorkerCount()` 将并行计算团队限制为最多 8 线程。`src/model/model_skinning.cpp` 的 PMX 蒙皮在顶点数至少为 16,384 时进入 OpenMP 并行循环。测试模型的 77,908 个顶点满足条件。`src/render/model_renderers.cpp` 中的透明排序也使用该团队。

默认模式的第一轮播放采样持续 12.005 秒，进程消耗了 88.844 CPU 秒。其中 7 个工作线程分别消耗 11.91～12.06 CPU 秒，接近持续满负载。7 个逻辑处理器本身就对应 21.875% 的整机容量，与额外占用的量级一致。

CPU 采样后的调用栈补充了等待位置的证据。

- 主线程的 258 个调用栈样本中，196 个停在 `SleepEx` 路径。
- 两个高占用工作线程各取得 258 个调用栈样本，其中分别有 115 个和 108 个落在 `VCOMP140.DLL` 的工作等待路径，其余主要在应用并行回调中。
- 本机 `VCOMP140.DLL` 版本为 `14.51.36247.0`。对热点所在 RVA `0x4724..0x47e5` 的只读反汇编显示，运行库反复执行 `pause` 和 `SwitchToThread`，用 `GetTickCount64` 检查约 100 ms 的等待期限，之后才转入 `WaitForSingleObjectEx`。

默认视口约每 16.7 ms 产生下一次帧工作，工作间隔短于上述主动等待期限。线程因此在帧间持续循环等待。`src/main/winmain.cpp` 中的 `Sleep` 只让主线程休眠，不能使 OpenMP 工作线程同时休眠。

`src/app/frame_driver.cpp` 的 `AdvanceFrameRenderGate()` 在默认未开启节省 CPU 选项时持续打开渲染门，所以模型静止也会继续更新视口。该持续刷新行为与线程主动等待共同造成了“没有播放却仍然很高”的占用。

被动等待对照保留相同团队和模型工作，7 个工作线程的 CPU 时间从每 12 秒约 12 CPU 秒降至约 0.3～0.6 CPU 秒。这个受控变量实验是主要归因依据。调用栈是墙钟抽样，不能把其中的比例直接当作 CPU 时间比例。

参考程序加载的是 `VCOMP90.DLL`，版本路径为 `9.0.30729.6161`。MMS 加载的是 `VCOMP140.DLL`。两份程序使用相似的并行循环，不代表其运行库的等待行为相同。

模型的物理规模确实较大，但在保留这些刚体、关节和相同物理模式的实验中，仅改变等待方式就消除了约 20 个百分点的 CPU 占用。物理规模无法解释这部分差值。

## D3DX 模块查询优化实测

原始记录：`PERFORMANCE_D3DX_2026-09-20.md`。其中的版本、日期和验证范围沿用原记录。

<a id="record-performance-d3dx-改动与原因"></a>
### 改动与原因

在 3532a36 基础上细分物理计时，人物样例的 PhysicsFrame 约 20 ms，其中
姿态更新约 11 ms、刚体回读约 6 ms，主 stepSimulation 仅约 2 ms。
这些路径频繁调用 D3DX 数学函数；每次 Api::Load 都重新调用
GetModuleHandleA("d3dx9_43.dll")，造成大量重复的模块查询。

静态导入已保证 D3DX DLL 在进程运行期间存在，因此只需首次获取模块句柄。
本轮仅缓存这一句柄，仍然在每次 Load 重新读取全部 IAT 函数入口，保留
MME 在设备创建之后安装挂钩的行为。动态加载分支保持原样。
没有修改数学函数、姿态计算顺序、物理步数、透明排序、资源格式或渲染质量。

新增默认关闭的 pose / physics_sync / physics_readback / physics_step /
bone_morph 计时。physics_step 仅包围主步进，不含初始化/settle/追帧步进；
这些基准的采样期主步进每帧一次。父子阶段包含关系与上一轮相同。

## Nex 思路的 D3D9 适配：第一轮

原始记录：`PERFORMANCE_NEX_ADAPTATION_2026-09-20.md`。其中的版本、日期和验证范围沿用原记录。

基于 ac8b14a。Nex 已确认使用计算着色器蒙皮、GPU 描边、命令/资源池以及
提交与等待分离。本轮借鉴资源复用和减少读写同步的原则优化本工程的透明
排序；**不是复刻 Nex 排序算法，也没有完成 D3D12/GPU 蒙皮后端**。
原参考证据见 REVERSE_PERFORMANCE_2026-09-20.md。

<a id="record-performance-nex-adaptation-实现"></a>
### 实现

- 每线程、每索引类型复用三角形和排序暂存数组，容量取历史最大值；不保存
  模型或 D3D 对象指针，模型删除/重载不会留下悬空引用。
- 大于等于 256 个三角形的材质使用四趟稳定字节基数排序，保留原浮点深度
  计算和同深度顺序。小材质仍用 stable_sort。正负零统一键值，非有限输入
  仍在写回前拒绝。
- 未加载 MMEffect.dll 时，在本模型不透明材质提交前准备排序索引，避免
  紧随本模型不透明 draw 后重新锁缓冲。已有投影阴影等绘制仍可能访问这些
  资源，因此不能宣称完全消除 GPU 同步。
- 有 MMEffect.dll 时保留原来的透明阶段排序时机，防止效果回调在两阶段间
